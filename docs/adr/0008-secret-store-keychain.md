# ADR-0008. Ключи секретных чатов в keychain ОС

Дата: 2026-10-31 · Статус: принято

## Контекст

Секретные чаты хранят на устройстве Olm-аккаунт, по одной сессии на чат, расшифрованную историю
и `CryptoKey`, которым запечатаны pickle'и. В браузере это IndexedDB (`web-secret-store.ts`):
данные лежат в профиле WebView, читаются кем угодно с доступом к профилю и не защищены, если
ноутбук унесли. DESK-7 просит keychain ОС.

Замерили, что реально лежит в сторе:

| scope | значение | особенность |
| --- | --- | --- |
| `secret` | `device` | публичные ключи устройства, ~0.3 КБ |
| `secret` | `account` | Olm account pickle под AES-GCM, ~12 КБ base64 |
| `secret` | `wrap` | non-extractable `CryptoKey` — в байты не сериализуется |
| `secret-chat` | состояние чата + session pickle, 2–5 КБ | |
| `secret-messages` | сообщения, у файлов `blob: Blob` | КБ–МиБ |

Отсюда следует, что «положить значения в keychain» нельзя: Windows Credential Manager принимает
2560 байт, macOS практически ~3 КБ на элемент, а `CryptoKey` вообще не имеет байтовой формы.
Хранить историю по элементам keychain тоже нельзя — нет перечисления и атомарности.

## Решение

1. **В keychain — один мастер-ключ.** 32 байта, service `app.orbit.desktop.secret-store`,
   account `master-key-v1`, создаётся при первом запуске. Крейты: `keyring-core` + платформенные
   store-крейты (`apple-native-keyring-store`, `windows-native-keyring-store`).
2. **Значения — файлы AES-256-GCM** в `app_local_data_dir()/secret/v1/<scope>/<sha256(key)>.bin`.
   Формат: `MAGIC|VERSION|nonce(12)|ciphertext`, AAD — `orbit-secret/v1\0<scope>\0<digest>`.
   Внутри `{ key, value }`, чтобы `keys(scope)` не расшифровывал лишнего. Имя файла — хеш, поэтому
   листинг каталога не выдаёт, какие чаты есть у человека.
3. **Запись атомарная**: temp-файл рядом, `sync_all`, `rename`. Каталог `0700`, файлы `0600`
   (Unix); на Windows ACL наследуется от `LocalAppData`.
4. **Пять команд** — ровно методы `PlatformSecretStore`: `secret_get/set/remove/keys/clear`.
   Белый список scope (`secret`, `secret-chat`, `secret-messages`), ключ не длиннее 200 символов
   и без разделителей пути: из web нельзя попросить записать файл куда-то ещё.
5. **`device` остаётся публичным.** Он и так известен серверу; держать его отдельным JSON рядом
   с файлами — значит не трогать keychain при старте и не получать prompt на каждом запуске.
6. **Миграция из IndexedDB** — в `entities/secret-session/model/migrate.ts`. Старым `wrap`
   открываем account и каждую сессию, новым (сырые байты в keychain-сторе) запечатываем заново:
   `CryptoKey` нельзя экспортировать, только пере-запечатать. Account пишется **последним**,
   поэтому прерванный прогон не выглядит завершённым и просто повторяется; старые значения
   удаляются только после того, как новые расшифровались.
7. **Ошибка ≠ пусто.** `SecretSession.open` теперь падает с `SecretKeyError`, если есть половина
   устройства (публичная часть без запечатанного аккаунта или наоборот). Раньше такой случай
   приводил к созданию нового устройства — то есть к молчаливой потере всех старых чатов.

## Что осталось за границей решения

- **История и вложения — тоже файлы.** Сообщение хранится как значение, а каждый `Blob` уезжает
  отдельным зашифрованным файлом рядом (`<scope>/<digest>.blobs/<имя>.bin`) и заменяется в JSON
  ссылкой `{ __orbitBlob }`. Поэтому перезапись сообщения не переписывает вложение, а
  `secret_remove` удаляет и файл значения, и каталог вложений. Цена: вложение идёт через IPC в
  base64 (33 МБ на 25 МБ файла) — для беты приемлемо, дальше можно перейти на raw-канал
  (`InvokeBody::Raw`), если появятся большие файлы. Предел одного вложения — 64 МБ.
- **Подпись и keychain.** ACL элемента привязан к подписи приложения: ad-hoc/неподписанная
  пересборка = новый identity, поэтому в dev возможен запрос доступа. С Developer ID и стабильным
  bundle id (DESK-10) запроса не будет. Удаление `.app` элемент не удаляет; почистить —
  `security delete-generic-password -s app.orbit.desktop.secret-store -a master-key-v1`.
- **Windows:** элемент создаётся с `persistence=Local` в `%LOCALAPPDATA%`; при домене roaming не
  используется. Пользователь может удалить элемент в «Управлении учётными данными» — тогда файлы
  перестанут расшифровываться, и приложение скажет об этом, а не создаст новое устройство.
- **XSS.** Команды доступны всему разрешённому origin; keychain защищает данные на диске и без
  работающего приложения, но не от вредоносного скрипта на странице.
- Автоформат истории (сжатие, ротация) не делались: файл на ключ и есть единица хранения.

## Проверено

- Rust: 12 юнит-тестов файлового хранилища (включая вложения и каскадное удаление) (round-trip, отсутствие = `None`, подмена байта = ошибка,
  идемпотентные remove/clear, запрет чужих scope и путей, имена-хеши, значение 20 КБ не ломается).
- Web: 7 тестов адаптера (маппинг команд, `locked → NotAllowedError`, `corrupt → DataError`,
  вложение как отдельный файл и обратно `Blob`) и 5 тестов миграции (пере-запечатывание,
  перенос истории с вложением, очистка IndexedDB, идемпотентность, чужой backend не трогаем).
- В живом приложении: каталог `~/Library/Application Support/app.orbit.desktop/secret/v1` создан с
  правами `0700`, элемент `app.orbit.desktop.secret-store` / `master-key-v1` появился в keychain.

## Ручная проверка

1. Чистая установка → новый device, элемент в Keychain, файлы в каталоге; перезапуск — тот же device.
2. Апгрейд со старыми чатами: список виден, чат открывается, собеседник не замечает смены ключа,
   старая IndexedDB очищена от ключей.
3. Убить приложение посреди миграции → повтор при следующем запуске, данные целы.
4. Заблокировать keychain / отказать в доступе → сообщение «ключи недоступны», **не** новое устройство.
5. Побить байт в файле → `DataError`, не пустой стор.
